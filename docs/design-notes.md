# P1 最小请求路径：设计与学习记录

整理日期：2026-10-11。范围是单连接、单请求的阻塞 TCP echo；使用 Linux 原始 socket API，直接练习消息边界、实际读写长度和文件描述符生命周期，不引入网络库或线程池。

## 协议

请求示例：`hello\n`；响应：完全相同的 `hello\n`。第一个 LF 是消息边界，第一条请求最多 1024 字节，包含 LF。空行 `\n` 按代码规则是合法请求；该案例尚未单独验证。按字节计数，不按中文字符数计数，也不校验文本编码。

找到 LF 时，检查 `newline_pos + 1 > 1024`；没找到时，`request.size() >= 1024` 就拒绝，因为至少还需要一个字节容纳 LF。超限或未完成就结束发送时，不回显已有片段，不发送错误响应文本。

只处理第一条请求。同一次接收中 LF 后的字节被丢弃，不支持流水线或一连接多请求。客户端应只发送这一条请求。

## 请求经过的路径

`socket → bind → listen → accept → recv 循环 → 确认完整请求 → send 循环 → close`

所有步骤在主线程执行。`recv` 按返回值追加字节，不能假设一次读取就是一条消息；`send` 按返回值增加偏移，不能假设一次调用发送全部响应。例如共 10 字节，第一次发送 4 字节，下一次从下标 4（第 5 字节）继续发送 6 字节。`MSG_NOSIGNAL` 避免发送时因 SIGPIPE 直接终止进程，失败仍需检查返回值。

## 资源与退出

`listen_fd` 表示监听 socket，`accept` 返回的 `client_fd` 表示已建立的连接，是两个独立的描述符。主函数负责关闭它们：接受连接前失败只关闭已创建的监听描述符；接受后失败或正常结束，关闭两者。程序退出也会回收描述符，但显式关闭有助于明确生命周期，防止未来长期运行时耗尽描述符等内核资源；这不只是普通堆内存泄漏问题。

正常回显后返回 0；创建、绑定、监听、接受、收发失败，以及不完整或超限请求，返回 1。当前对系统调用失败直接退出，尚未针对 EINTR 重试。

## 已知限制与待补项

- 每个进程只接受一次连接；下一次测试需要重新启动，未实现持续接受连接。
- 没有服务端读写超时；客户端连接后不发送完整请求可能一直阻塞。
- 未设置 SO_REUSEADDR，部分快速重启场景可能发生地址占用。
- 没有 EINTR 重试、RAII 封装、并发、线程池、TLS、持久化或性能结论。
- `close` 遇到尚未读取的客户端数据时，客户端可能看到连接重置；未承诺所有非法输入都以正常 EOF 结束。
